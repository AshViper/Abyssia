差異・修正点

【高】発光線の「送電方向」の表現を仕様に合わせて確認・固定する

2枚目・3枚目では光の粒が受け側へ流れているため、見た目としては仕様どおり。
ただし仕様上は「送電方向に沿って光が流れる」であり、FEの実際の送電方向と粒子の流れる方向が常に一致することが必要。
特に A ⇄ B の双方向送電で毎 tick 方向が変わる場合、表示だけが逆方向になるケースがないか確認する。
修正: Renderer が actualTransferDirection を参照して、送信側アンテナ → 受信側アンテナへ粒子を流す。

【高】「送電なし」の発光線をもう少し暗くする

1枚目を見ると idle 状態でも線がかなり視認でき、2枚目の送電中との差がやや小さい。
仕様は「リンク成立のみ = 暗め」「送電中 = 明るくなる」なので、状態差をもっと明確にした方がよい。
修正案:
idle: 現在の 50～60%程度の輝度
transmitting: 現在の明るさを維持
粒子: idle は無し、送電中のみ表示

【中】発光線の太さがデザイン画・仕様よりやや太く見える

2枚目・3枚目では線本体が比較的太く、特に近距離部分では「レーザー／ビーム」に近い見た目になっている。
仕様は「青緑色の細い発光線」「約1～2 pixel相当」。
修正案: 通常線を1段細くし、発光のグローだけで存在感を出す。
ただし、ゲーム画面上で視認性を優先するなら現状でも許容範囲。

【中】発光線の「わずかな揺らぎ」がスクリーンショットでは確認できない

2枚目・3枚目では光粒の移動は確認できるが、線そのものの微細な揺らぎは確認しにくい。
仕様には「わずかな揺らぎ」を明記しているため、実装していない場合は追加。
大きく蛇行させる必要はなく、数px程度の非常に小さい位相変化で十分。

【中】デザイン画に対してアンテナ形状が簡略化されている

デザイン画では最上部が「十字/リング状」のアンテナで、中心コアを囲む構造。
実機は十字型として成立しているが、リング状の外周構造はほぼ見えない。
仕様上は「十字/リング状」なので致命的ではないが、デザイン画との一致を重視するなら、4方向の腕をもう少しリング状に見える構成へ寄せる。

【中】筐体の銅色がデザイン画より明るく、面積もやや大きい

実機では銅色の外周補強がかなり目立つ。
デザイン画の想定は「暗い青灰色の筐体 + 暗銅の補強」で、青灰色が主色。
現状は遠景でも銅色が強く見えるため、Abyssia の他設備との統一を考えるなら銅の彩度・明度を少し落とすのがよい。
優先度は見た目調整なので中。

【中】1枚目の三角形リンクでは、遠距離リンクの線が地形・植物の背後を貫通して見える

これは仕様どおりで、視線遮蔽を行わない無線なので機能上は問題なし。
ただし実機では発光線が地形に重なった際に視認性が高く、かなり「レーザー」っぽく見える。
修正するなら遮蔽ではなく、線の不透明度を少し下げる程度に留める。
壁・地形でリンクを切る仕様には変更しない。

【低】リンク線の最大表示距離96mと最大リンク距離128mの差をゲーム画面だけでは確認しにくい

これは実装上の問題ではなく、テスト項目不足。
96～128mのリンクを作り、送電は成立するが発光線だけ消えることを1ケース確認すると仕様検証が完了する。

【低】「リンクなし時」の見た目について、実機確認ケースが不足

仕様では「アンテナ先端は弱く発光」「発光線なし」。
今回は idle のリンク中を確認できているが、リンク相手が一切存在しない単独WR01のスクリーンショットがない。
単独設置でコア/アンテナが弱発光になることを確認しておく。

【高】破壊時の「上下2ブロックとも消える」処理は、BlockEntity/マルチブロック状態を必ず検証する

仕様では1基の WR01 が高さ2ブロックなので、破壊時に2ブロックが消えること自体は正しい。
ただし、上段だけを破壊した場合・下段だけを破壊した場合の双方で完全に1基として除去されるかを確認する必要がある。
特に Forge の BlockEntity が下段にある場合、上段破壊 → 下段 BlockEntity 残存、という孤立状態を作らないこと。

【高】「充填率の高い方から低い方へ」の実装単位を明確化する

実測では「拠点共有FEと1,024FEバッファの間で充填率の高い方から低い方へ」となっている。
仕様書では「余剰エネルギー側から不足側」としていたため、実装が本当に current / max の充填率比較になっているか確認した方がよい。
特に HabitatPower 1,000,000 FE と WR01 1,024 FE を単純な残量比較すると、ほぼ常に HabitatPower 側が「高い」と判定されるため、残量ではなく明示的な充填率を比較する必要がある。
ここは実装仕様としてかなり重要。

【高】多段中継時のFE二重取り・循環をテストする

三角形リンクは今回確認できているが、A → B → C → A の循環が成立しているため、仕様にある「同一tick内で同一WR01を2回以上通過しない」が重要。
特に A/B/C 全てに1,024FEバッファがある状態で、毎tickの充填率比較を行うと、FEが三角形を高速循環する可能性がある。
FE総量が送電損失を除いて増減しないことを確認するテストを追加する。

【中】128m超で「リンクしない」は確認済みだが、境界値128mちょうどを確認する

現在の「128m超はリンクしない」は仕様に合っている。
ただし境界条件として、
127.99m → 接続
128.00m → 接続
128.01m → 非接続
の扱いを確認しておくと安全。
Minecraft の座標距離計算で平方根を毎回使わず、距離二乗比較にしている場合の境界値も要確認。

【低】「近い順」のタイブレーク規則が未定義

3基三角形では問題ないが、同じ距離に3基以上存在した場合、どの2基を選ぶかが仕様書では決まっていない。
修正案: 距離 → BlockPos の辞書順 など、決定的なタイブレークを設定する。
これによりサーバー再起動後などにリンク先が不安定になるのを防げる。

【中】送電粒子の数は距離・送電量に応じて上限を設ける

3本程度なら問題ないが、WR01が多数設置された環境では、リンク数 × 光粒子数が描画負荷になる。
仕様の「性能上の制約」に対して、1リンクあたりの最大粒子数が未定義。
修正案: 1リンクにつき同時表示する光粒を最大数個程度に固定し、送電量によって速度だけ変える。
粒子数をFE/tに比例させる実装は避ける。
